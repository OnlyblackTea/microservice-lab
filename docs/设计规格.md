# 微服务治理八股 · Track 设计规格

> 状态：设计稿（未开工）· 对应平台契约见 [`_CONTRACT.md`](./_CONTRACT.md)
> 一句话定位：给「Spring Cloud 全家桶背得很熟、但没亲手让一个熔断器真的跳闸过」的 Java 后端——
> 三个进程（网关 / 订单 / 库存）就是他真实的微服务，治理能力缺一块就有一个用例红着等他补。

> [!IMPORTANT]
> 这份规格最重要的两节是 §1.0 的**两个取舍论证**（资源门槛、与 `mq-lab` 的重叠）。
> 先有结论，才有下面 5 张工单；结论一旦不成立，本文档剩下的部分就该被丢掉而不是打折执行。

## 0. 一页纸摘要

| 项 | 值 |
|---|---|
| track.id | `microservice-bagu` |
| 骨架仓名 | `microservice-lab` |
| 目标岗位 / 面试方向 | Java 后端 3-5 年、偏「分布式 / 微服务治理」；面试里被问「你们熔断怎么配的、限流打在哪一层」时能说自己调过 |
| 语言栈 | Java 17 + Maven（多模块）+ Spring Boot 3.2.5 + JUnit 5 / Surefire `-Dgroups=stageNN` |
| 基础设施 | **默认档：零外部容器**（只跑 JVM）。常用档：`mysql:8.0@13306` + `redis:7@16379`（复用 `seckill-lab` 的端口约定）。演示档：`nacos/nacos-server:v2.x`（选修，不进判据） |
| stage 数 | **5 个**（Stage 1–4 为判据主干，Stage 5 为**选修**；另有 1 个 board-only 的 `stage-00-onboarding` 只上看板） |
| 依赖前置 | `java: "17"` / `build: maven` / `docker: "24"`（仅常用档与演示档需要）/ `memory_gb: "4"`（见 §6.4） |
| 与 database-bagu 的关系 | 无重叠。`seckill-lab` 覆盖的是「单个进程 + 一个数据库」的深水区（索引/事务/锁/MVCC/缓存/死锁）；本 Track 的对象是**进程之间**（实例列表、超时、熔断、限流、traceId），两边唯一的共同词汇是「幂等」 |
| 与 mq-lab 的关系 | **重叠已被切干净**（论证见 §1.0.2）：幂等写入 / 去重表 / 最终一致性 / 消息重投全部划归 `mq-lab`，本 Track 只留治理面 |
| 预计落地工作量 | 骨架 6 人日 / canonical 测试 5 人日 / 题面与判据 2 人日 / 分支与 pin 1 人日 ≈ **14 人日** |

**卖点（三条以内）**

1. **抖动指标被换成了确定的结构**：熔断不看「多少毫秒后恢复」，看「滑窗里连续几次固定延迟的下游错误之后，请求是否不再发出去」；限流不看 QPS，看「注入时钟推进到补充周期后额度恰好恢复」——治理考点第一次有了能进 canonical 测试的判据。
2. **学员机器的门槛被压到「一个 JVM」**：三服务 + 注册中心 + 网关的 compose 常驻内存 >2GB、冷启动 >2 分钟，与设计前提 D3（用学员自己的算力）冲突；本规格把默认档压到约 1.2GB / 90 秒以内，注册中心用静态实例列表等价替代（为什么等价，见 §1.0.1）。
3. **每个 stage 都红在一个真实的治理缺陷上**，不是「TODO 没实现」：轮询退化成固定打第一台、下游慢下来时请求一路裸奔、同一个人能刷爆下单接口、三台机器的日志谁也认不出谁。

> 与 [`README.md`](./README.md) 选题总览的对账：该表把本条 Track 记作「4~6 个 stage、判据确定性 ★★★☆☆」。
> 本规格的落地结论是 **5 个 stage（4 主干 + 1 选修）**，星级维持 ★★★☆☆——因为 §1.4 列出了三项只能「可观测」的考点（Zipkin UI、
> 熔断恢复时机、控制台规则推送）。开工时应把 README 该行的 stage 数从 `4~6` 改成 `5`。

## 1. 判据可行性论证（最重要的一节）

### 1.0 两个先决取舍

#### 1.0.1 取舍一：资源门槛——把「注册中心 + 网关 + 服务」的 compose 砍成一个 JVM

**问题是真的。** 微服务八股的教科书拓扑是「Nacos + Gateway + N 个服务 + Sentinel 控制台 + Zipkin」，
按 Spring Boot 3 单进程 RSS 200–400MB 的经验值估算（见 [单个 Spring Boot 应用的资源占用实测讨论](https://blog.zouaw.com/article/109815.html)、
[Nacos 内存参数调优](https://cloud.tencent.com.cn/developer/article/1913455)、
[2 核 2G 跑 Docker + 微服务的讨论](https://blog.27nk.com/article/108886)），这套拓扑的**常驻内存**是：

| 组件 | 常驻内存（估） | 冷启动（估） |
|---|---|---|
| Nacos standalone（JVM 版） | 500–900MB | 30–60s |
| 三个 Spring Boot 服务（gateway + order + stock） | 3 × 250–400MB = 750MB–1.2GB | 3 × 8–20s |
| Sentinel 控制台（若引入） | 200–400MB | 10–20s |
| Zipkin 服务端（若引入） | 200–300MB | 5–10s |
| MySQL 8 + Redis 7 | 350MB + 10MB | 30–80s（含 init） |
| **合计** | **2.0–3.2GB** | **1.5–3 分钟** |

D3 的前提是「用学员自己的算力」，而「8GB 笔记本 + 同时开 IDE」是常见下限：2GB 交给容器、IDE 再吃 1.5GB，
机器就会开始换页，`docker compose up` 之后的第一次 `mvn test` 会因为超时而**假红**——这正是本 Track 最该避免的失败模式。

**瘦身方案（这是本规格的硬承诺，不是建议）：**

| 决策 | 做法 | 省下什么 |
|---|---|---|
| **注册中心：不进判据，用静态实例列表等价替代** | 服务的实例清单写在 `application.properties` 的 `stock-service.instances` 里，由 Spring Cloud LoadBalancer 消费。**注册发现的「位置」被配置源（`@ConfigurationProperties` + `@RefreshScope`）替换** | 省掉 Nacos 进程的 500–900MB 与 30–60s；同时让「实例列表变了要不要重启」变成 Stage 5 的考点 |
| **Nacos 只做演示档** | `docker/docker-compose.nacos.yml`（单独文件，**不写进 `runtime.compose`**），学员想验证「配置推送到客户端」时手动起 | 判据不依赖它，机器不够就不开 |
| **熔断：只用 Resilience4j 库，不引入控制台** | Resilience4j 是纯函数式容错库、状态机在进程内（其[官方定位](https://github.com/resilience4j/resilience4j)就是「为函数式编程设计的容错库」），没有必须引入的独立控制台 | 省掉 200–400MB；而且进程内状态机**可编程断言**，比控制台更适合当判据 |
| **限流：自研令牌桶，不引入 Sentinel** | Sentinel 的核心价值（控制台、规则持久化、集群限流）都超出「单机限流」这一考点，而它的 agent 是运行时字节码增强 | 省掉 200–400MB + 一个字节码 agent（对「判据可复现」是负担） |
| **链路追踪：不引入 Zipkin / Sleuth / Micrometer Tracing 的导出器** | 断言的对象是「traceId 在同一条链路的日志里可关联」，不是 UI 上的火焰图。采集端用进程内的日志事件收集器 | 省掉 200–300MB + 一个 HTTP 上报依赖（也就避免了「判据依赖网络」） |
| **数据库：判据默认不用它** | 唯一键只在 Stage 5 用，且由 canonical 测试提供内存实现（`InMemoryOrderRepository`） | 默认档连 MySQL 都不需要 |

**瘦身后的三档预算（学员机器口径）：**

| 档 | 内容 | 常驻内存（估） | 冷启动 → 跑完一个 stage（估） |
|---|---|---|---|
| **默认档（判据档）** | 1 个 Maven JVM，内含 2 个 Spring Boot 上下文（order + stock，端口随机） | **1.1–1.4GB** | 40–70s（`~/.m2` 预热后更快） |
| **常用档（手玩档）** | 默认档 + `mysql:8.0@13306` + `redis:7@16379` | **1.5–1.9GB** | 90–150s（MySQL 首次 init 约 20–40s，表从简，不灌大种子） |
| 演示档（选修） | 常用档 + Nacos standalone | 2.0–2.8GB | 2–3 分钟 |

**如果仍然超预算，砍的顺序是明确的**（从先砍到后砍）：

1. 先砍 **Stage 5（选修）** —— 它承担「分布式 ID + 唯一键兜底」，重要性最低，且唯一键兜底已归 `mq-lab`；
2. 再砍 **Stage 4（链路追踪）的 canonical 测试**，降级为「只可观测」——它本来就是本文档里最偏观测面的一个考点；
3. 最后砍 **网关进程**（把 gateway 降级成 order 服务里的一个过滤器，或干脆删掉），只留 order + stock 两个上下文。

**绝不砍的是**：Stage 1（实例列表 + 负载均衡）与 Stage 2（超时 + 熔断）——前者是唯一能证明「这是微服务而不是单机项目」的 stage，
后者是这条 Track 最硬的判据（计数窗口不依赖时间）。**砍到只剩一个 stage 时，停在 Stage 2。**

#### 1.0.2 取舍二：与 `mq-lab` 的重叠——本 Track 只剩「治理面」，重叠考点明确划归

`mq-lab`（消息队列与最终一致性）已经吃掉了整片「幂等 / 去重 / 最终一致性」。本 Track 的原始候选里
Stage 5 写着「分布式 ID 与幂等（雪花 / 号段模式，唯一键兜底）」，**「幂等」这两个字就是重叠点**，必须切。

| 考点 | 谁覆盖 | 切分依据（一句话） |
|---|---|---|
| 消费端幂等 | **mq-lab** | 幂等的载体是「同一条消息被投递两次」，没有消息就没有这个现象；在 HTTP 服务里演示它只会做成一个假的 MQ |
| 去重表 / 唯一键去重 | **mq-lab** | 去重表是**消费侧**的模式（消息 id 唯一键 + 消费记录），它的设计约束（表增长、清理、与业务写入同事务）只在 MQ 语义下才成立 |
| 最终一致性 / 本地消息表 / 事务消息 | **mq-lab** | 需要「消息中间件 + 重投」才谈得上「最终」 |
| 重试与死信 | **mq-lab** | 同上 |
| 分布式 ID 生成（雪花 / 号段 / 时钟回拨） | **本 Track** | `mq-lab` 不需要它；它是「多节点共享一个 ID 空间」的问题，属于服务间协作 |
| 唯一键作为**兜底**（订单号冲突） | **本 Track**，只作为 Stage 5 的一条断言 | 它验的是「唯一索引挡下之后有没有第二条路」；题面明确禁止建去重表、禁引 MQ（§4.5） |
| 服务注册发现 / 实例列表 | **本 Track** | `mq-lab` 无此面 |
| 客户端负载均衡（轮询 / 故障摘除） | **本 Track** | 同上 |
| 超时 / 熔断 / 降级 / 隔离 | **本 Track** | 同上 |
| 限流（单机令牌桶 / 漏桶 / 滑动窗口） | **本 Track** | 同上 |
| 链路追踪 / traceId 透传 / 日志串联 | **本 Track** | 同上 |
| 配置热更新 / 灰度 | **本 Track（只讲不判）** | 同上 |

**边界落地方式（三条，缺一条切分就会漂回去）：**

1. `track.yaml` 的 `manifest.stages` 只列本 Track 的 5 个 stage；需要交叉引用 `mq-lab` 时用**外链**形式
   （指向那份规格/地图的锚点），不在本 Track 里再写一遍考点表。
2. 本 Track 八股地图末尾那节「不涉及但你该文字了解」**显式点名** `mq-lab` 覆盖的四项，并写明「这里不讲，是因为它在那边有真实现象」——
   把重叠写成**指针**而不是两边各写一份（呼应 `_CONTRACT.md` §7「事实只存一份」）。
3. Stage 5 的题面里写清范围禁令（不许引入消息队列、不许新建表），否则学员的自然解法就是从 `mq-lab` 借答案过来，
   而那条判据在本 Track 里没有对应的现象支撑。

**如果评审认为仍然不够独立，替代方案（本文档给出口，但不推荐采用）：**
把 Stage 2（超时 + 熔断）与 Stage 3（限流）拆出来，作为 `mq-lab` 的 `stage-07/08`，
理由是「MQ 消费者也需要熔断与限流」。**不推荐的理由有两条**：
① 并入后 `mq-lab` 变成「消息 + 治理」的混合 Track，它的机器门槛从「MySQL + Redis」被抬到「还要两个服务上下文」，
`mq-lab` 学员的体验被本 Track 的问题污染；② `mq-lab` 的骨架是「生产者 + 消费者 + MQ」，
把「订单 + 库存 + 网关」塞进去等于在一个仓里养两套业务语义，而**Stage 1（实例列表 / 负载均衡）在那边根本没有宿主**——它不属于 MQ 的任何一面。

**§1.0.2 的结论：独立成 Track（收窄版），不并入 `mq-lab`。** 理由三条，按分量排序：

1. **重叠已经被切干净，而且切分有依据**：剩下的六个面（注册发现 / 负载均衡 / 熔断降级 / 限流 / 链路追踪 / 分布式 ID）
   在 `mq-lab` 里一个都没有宿主——它们需要「服务调用服务」这个场景，而 MQ 骨架里的调用是「生产者发消息、消费者收消息」，
   没有实例清单、没有超时、没有配额。硬并过去只会让两边的骨架互相污染。
2. **判据能站住**：四个主干 stage 的红都红在业务缺陷上（选路、熔断、配额、可关联性），
   而且抖动指标已被换成确定结构（计数窗 / 注入时钟 / 集合断言，§1.3）。这不是一条「只能靠嘴讲」的 Track。
3. **代价是明确的、并且被接受了**：判据档要跑两个 Spring Boot 上下文（1.1–1.4GB），
   因此换来三条让步：真注册中心与 Sentinel 控制台不做判据（§1.4）、Stage 5 降为选修、
   砍 stage 的顺序事先写死（§1.0.1）。**这三条让步是这条 Track 能成立的前提，不是可选项。**

**不采纳「并入 `mq-lab` 作两个 stage」的理由**：那样做的收益只是省一次骨架搭建，代价是
① `mq-lab` 变成混合 Track、机器门槛被抬高；② Stage 1（实例清单 / 负载均衡）无处安放；
③ 本 Track 最硬的判据（Stage 2 的计数窗熔断）会变成 MQ 课程里的一个附带小节，学员失去「治理是一条独立能力线」的认知。
**唯一的例外**是 §1.1 的拓扑在目标机器上被证伪（默认档压不进 4GB）——那时才先走替代方案
（把 Stage 2/3 并入 `mq-lab`），并把 Stage 1/4/5 留作后续独立切片。

### 1.1 判据骨架：两个进程、一个 JVM（canonical 测试的真实拓扑）

这是本文档最关键的一个工程决定，因为它决定了「红」到底红在哪。

**canonical 测试不能依赖「外面已经起好了两个服务」。** 如果 `mvn test -Dgroups=stage02` 要求学员先手动起 JVM，
那学员没起的时候测试会红在 `Connection refused`——这是**假红**：红在环境没起来，而不是红在治理缺陷上。
准入门（`_CONTRACT.md` §4「测试判别性」）要的是「骨架红 / 参考解绿」，`Connection refused` 会两边都红，直接废掉这条 Track。

**因此 canonical 测试的拓扑固定为：单个测试 JVM，进程内拉起两个 Spring Boot 上下文。**

```java
// src/test/java/com/devteam/micro/lab/LabRuntime.java（判定面，学员不可改）
// 约定（skeleton 与 canonical 测试共同的契约）：
//   1) 测试用 SpringApplicationBuilder 起 stock 上下文：
//        .properties("server.port=0", "spring.application.name=stock-service",
//                    "lab.instance.id=stock-a")  → run()
//      再从上下文里读 WebServerApplicationContext.getWebServer().getPort() 拿到真实端口。
//      order 上下文同理（server.port=0，spring.application.name=order-service）。
//   2) 通过 @DynamicPropertySource 把
//        "stock-service.instances[0]=http://127.0.0.1:<stockPort>"
//      注入 order 上下文——**实例列表来自配置**，这正是真实注册中心的等价物。
//   3) 需要「两台库存实例」的用例再起第二个上下文（server.port=0，服务名相同，
//      lab.instance.id=stock-b），实例列表里就有两个 URL。
//   4) 需要「一台挂掉的实例」的用例，实例列表里放一个 http://127.0.0.1:<未监听端口>。
//   5) 下游故障由库存侧的测试专用端点 POST /internal/fault 注入（见下），不靠杀进程、不靠真实网络抖动。
```

> **实现风险与备选方案（必须写下来，别让它变成开工当天的意外）**：`@DynamicPropertySource` 要求测试
> 自己能在**上下文创建之前**拿到下游端口，这与「先起上下文再注入属性」天然循环。因此实现优先走上面第 1 条的
> **显式手动起上下文 + 把 base-url 放进一个可变的 `AtomicReference` 属性源**（`LabRuntime` 提供
> `MutablePropertySource`，order 上下文用一个 `@ConfigurationProperties` 的 setter 在起完之后被写入）；
> 若这条在 Spring Boot 3.2 上仍然打架，则退到**备选方案 B**：把「实例列表」的读取点做成骨架里一个
> `InstanceListProvider` 接口（判定面提供 `MutableInstanceListProvider` 实现），测试直接注入实例列表，
> 而 Stage 1 的题面与判据不变（仍然只验「选路与摘除」，只是实例列表的来源从配置文件换成同形态的注入点）。
> **备选方案 B 是安全网，不是首选**：它会让 Stage 1 少一个「实例列表写在配置里」的教学点，所以只在 A 被证伪时使用。

**下游故障怎么做到确定（这是全部抖动风险的根）：** 库存服务的**测试作用域**里有一个故障注入器
（`stock-service/src/test/java/com/devteam/micro/stock/lab/FaultController.java`，属于判定面），它只做三件事：
把某个代号的响应变成固定状态码、固定延迟、或固定次数的 5xx。固定值全部写成常量：

```properties
# src/test/resources/lab-fault.properties（判定面）
lab.fault.slow.delay-millis=600      # 固定 600ms；订单侧读超时固定 300ms、连接超时固定 200ms
lab.fault.error.status=500
lab.fault.error.times=5              # 只失败 5 次（供 H3 的手工观察用；canonical 断言不依赖它）
lab.limiter.clock.seed-millis=1700000000000   # 限流器注入时钟的起点（常量，与真实时间无关）
```

**为什么固定 600ms / 300ms 就够了**：判据不是「600 是不是抖动」，而是「**订单侧在 300ms 就放弃，
并把这次失败交给容错组件统计**」。下游再慢也不会改变「读超时必然触发」这个结构性事实——
延迟只负责「让下游一定会超时」，它的大小不参与任何断言。这就是把抖动指标换成确定结构的办法。

**不做的事（明确写下来，避免后来者「顺手加上」）：** 不引入 Testcontainers（会引入镜像与 Docker 依赖）、
不引入 WireMock（会引入一个「假下游」，让 Stage 1 的「真实例」失去意义）、不引入真实 MQ、
不联网拉依赖以外的任何东西（依赖预热见 §6.3）。

### 1.2 逐 stage 红绿形状

| stage | 骨架红在哪（哪个用例、缺了什么） | 为什么「红在对的地方」 | 参考解绿成什么形状 |
|---|---|---|---|
| **1** 实例列表 + 负载均衡 | `stage01/LoadBalancerRoundRobinAcceptanceTest#roundRobin_alternatesBetweenTwoInstances` 红：实例清单里有两台健康库存，但三次调用全部落到同一台（响应头 `X-Lab-Instance` 三次都是 `stock-a`）。缺的是「按清单顺序挑下一台」 | 编译通过、两个上下文都起来了、HTTP 200 拿到了正确结果——**只有「选谁」这一件事错**。不是装配失败，也不是端口没通。同 stage 的 `LoadBalancerFailoverAcceptanceTest` 红在同一个根因的另一种表现 | 三次调用依次命中 `stock-a / stock-b / stock-a`（顺序周期，不是「两台都出现过」）；清单里放一个死地址时连打八次全部成功、0 次异常、0 次落到死地址 |
| **2** 超时 + 熔断 + 降级 | `stage02/CircuitBreakerAcceptanceTest#circuitOpens_afterConsecutiveTimeouts` 红：注入固定 600ms 延迟后连发 12 次，12 次都真的发到了库存（`X-Lab-Calls` 从 0 涨到 12），调用方 12 次都拿到异常。缺的是「超时不再向上抛而是记一次失败；连续失败达到阈值后不再发请求、直接走降级」 | 红在一个真实的生产事故形状上：下游慢 → 上游线程被等干 → 上游自己也垮。骨架两条都犯（没有超时、没有熔断），但进断言的只有熔断那一条（超时的作用见 §1.4） | 阈值之后每一次请求都在远小于 300ms 内返回、`X-Lab-Calls` **停止增长**（这一条才是熔断的定义）、返回 HTTP 200 + 可区分的业务态；降级返回不写任何订单 |
| **3** 限流 + 过载保护 | `stage03/RateLimitAcceptanceTest#burst_beyondCapacity_isRejected` 红：同一身份连发 20 次、容量固定 10，骨架放行 20 次（`X-Lab-Calls` = 20），期望 10 过 10 拒。缺的是「判定与桶的状态相关」 | 红在「限流器形同虚设」，不是「没装配」：桶、容量、速率、时钟都已经接好，唯一缺的是判定逻辑。同 stage 的 `OverloadIsolationAcceptanceTest` 红在配额维度上 | 20 次恰好 10 过 10 拒；被拒的请求 0 次触达下游；注入时钟推进到补充周期后恰好再放行 10 次；换一个身份不受影响；被拒请求 0 写库 |
| **4** traceId 透传 + 日志串联 | `stage04/TraceIdPropagationAcceptanceTest#wholeCallChain_sharesOneTraceId` 红：带已知 traceId 请求时响应头回显的值与请求不同、日志事件里该标识为 `null`、下游那条日志也没有它。缺的是「把标识落到日志上下文并带到下游」 | 红在「可关联性」这一件事：请求活了、业务结果对、三个组件都写了日志，但没有任何一条能把它们串起来。同 stage 的 `LogCorrelationAcceptanceTest` 红在同一根因 | 沿用上游标识时全链路一致且响应头回显同一值；不带时生成 32 位小写十六进制并由下游沿用（不是每跳重新生成）；该 traceId 下的日志事件**每一条**都含它，且至少来自两个组件 |
| **5** 分布式 ID + 唯一键兜底（选修） | `stage05/DistributedIdAcceptanceTest#idIsUniqueAndTimeOrdered` 红：同一毫秒生成 200 个 id，唯一数 < 200；解析出的实例段与 `lab.instance.id` 不符；时钟回拨后出现逆序 id | 红在 id 的三个**可判定性质**（唯一 / 可解析 / 时间有序）上，不在「用不用雪花」这个选择上——号段模式只要能过同一批断言就算过 | 同毫秒 200 个 id 全唯一；三段解析与配置、注入时钟一致；时钟回拨时「明确拒绝」或「等到追上」两条路都判绿，只看有没有逆序 id；冲突后重试不把错误抛给用户 |

### 1.3 确定性论证（逐 stage：为什么多次跑结果一致）

| stage | 唯一的抖动来源 | 怎么让它确定 |
|---|---|---|
| 1 | 两个实例的端口、Tomcat 线程调度 | 端口由 `server.port=0` 分配后**从上下文里读真实值**再写进实例列表；断言看的是**顺序周期**（A,B,A）而不是耗时或「谁先谁后」 |
| 2 | 熔断器的滑动窗口默认按**时间**统计 | 测试里显式配置 `slidingWindowType=COUNT_BASED` + `minimumNumberOfCalls` + `slidingWindowSize`——**计数窗没有时间维度，就没有抖动**；`waitDurationInOpenState` 取一个测试期间不会自然到期的大值（如 60s），于是「打开后不再发请求」这条断言在测试期间恒成立 |
| 2 | 下游延迟是真实 sleep | 延迟（600ms）与读超时（300ms）都是常量；断言只看「是否触发超时分支」与「后续是否还发请求」，从不看耗时数值 |
| 3 | 令牌桶的真实时间 | 桶的时钟是**注入的 `LabClock`**（骨架提供、判定面）：测试显式 `clock.advance(...)` 而不是 `Thread.sleep(...)`。这一条把限流从「抖动考点」变成「纯函数考点」 |
| 4 | 日志事件的顺序、异步 appender | 断言的是**集合**（该 traceId 下每条事件都含它），不是顺序；测试方法之间清空收集器；Surefire 关并行（`-Dparallel=none`，写进 `pom.xml`） |
| 5 | 同一毫秒内序号耗尽、真实时钟 | 生成器持有**注入时钟**（`LabClock` / `ControllableClock`），测试用它制造「同一毫秒内 200 次生成」与「时钟回拨」两个场景。序号在同一毫秒内耗尽时转向下一毫秒（不判红），这一条写进断言注释 |

### 1.4 只能「可观测」、不能进 canonical 测试的考点（诚实清单）

| 考点 | 为什么不能进判据 | 替代做法 |
|---|---|---|
| Zipkin / Jaeger UI 上的火焰图与依赖拓扑 | 需要采集服务端 + 浏览器 + 网络上报；判据不能依赖公网与图形界面 | 提供 `docker/docker-compose.observability.yml`（单独文件、不进 `runtime.compose`）；地图的「复现命令」给 curl，学员想看就自己起 |
| 半开 → 关闭的**恢复时机**（毫秒级） | 依赖真实时间与调度 | 进判据的只有「打开后不再发请求」；「多久之后允许探测」写进 hint 与地图考点，canonical 把 open 窗口设得足够大以保证测试期间不会自然到期 |
| 超时值的调优（300ms 够不够） | 绝对延迟是抖动指标 | canonical 只断言「超时分支被走到」；300ms 在题面里是给定常量，不是待调参 |
| Sentinel / Nacos 控制台上「规则有没有推下去」 | 需要控制台进程 | 演示档手动验证；Stage 5 只讲不判 |
| 灰度权重分流「看起来均不均」 | 概率分布 | Stage 5 只讲不判；若将来要判，判据只能是「固定 seed 的分配表」，不是统计比例 |
| 真实网络分区、K8s readiness gate、服务网格 sidecar | 需要集群 | 不涉及（并在地图「不涉及」一节里点名） |
| 「代码跑得比故障注入快」这类竞态 | 时序协调 | 用固定延迟（600ms）而不是「等下游卡住」；`/internal/fault` 在返回前同步写好状态（`AtomicReference`），不存在「写还没生效」的窗口 |

> 融合，且**保留这条 Track 独立存在的理由**（Stage 1 需要一个「服务与服务之间」的宿主，MQ 骨架给不了）。
> **替代方案的触发条件**：只有「Stage 1 的实例列表与负载均衡在低配机器上压不进默认档」时才走它——
> 而不是因为「考点不够多」。完整的取舍结论见 §1.0.2 末尾。

### 2.2 分层与约定

`docs/架构与约定.md` 里写清四条铁律（对应 `seckill-lab` 的同名文档）：

1. **HTTP 客户端只出现在各服务的 `client` 包**，`service` 包不许出现 `RestClient` / `RestTemplate` / `HttpClient` 类型——
   这样「下游调用怎么发」只有一个地方可改，Stage 1/2/4 的改动面才收得住。
2. **所有时间来源走 `LabClock`**（`instant()` / `millis()`），业务代码里禁止 `System.currentTimeMillis()`——
   这是 Stage 3 与 Stage 5 能进 canonical 测试的前提。
3. **日志一律用参数化占位**（`log.info("deduct productId={} traceId={}", ...)`），不拼字符串。
4. **响应体统一 `{code, data, message}`**：降级用 `code=DEGRADED` + HTTP 200，限流用 HTTP 429 + `code=RATE_LIMITED`。
   这两条是 Stage 2 与 Stage 3 判据的观测面，先定死比事后解释便宜。

### 2.4 基础设施

- **默认档**：无容器。canonical 测试用进程内上下文 + `InMemoryOrderRepository`（唯一键语义由 `ConcurrentHashMap` + 显式冲突注入实现）。
- **常用档**（`docker/docker-compose.yml`，端口沿用 `seckill-lab` 的避让约定）：
  `mysql:8.0` 宿主 `13306`→容器 `3306`（`micro_order` / `micro_stock` 两库，**表从简**：
  `micro_order(id, user_id, product_id, quantity, uk_user_product)`、`micro_stock(product_id, stock)`，种子 20 行以内），
  `redis:7` 宿主 `16379`→容器 `6379`。
  MySQL 的 healthcheck **必须**用 `127.0.0.1` 强制走 TCP（`seckill-lab` 踩过：`-h localhost` 走 socket，
  会在 init 还没跑完时误报 healthy）。
- **演示档**（选修、单独文件、不进 `runtime.compose`）：`nacos/nacos-server:v2.x` standalone（宿主 `18848`→`8848`，
  避开 8848/9848 常见占用）与 `zipkin`（宿主 `19411`→`9411`）。这两份文件属于判定面（防止有人用它们改写判据路径），
  但**不在 `runtime.compose` 里**，因此不需要对应的 `digest_pin` 入口——它们只在 §6.2 的「可选镜像」里 pin 摘要。

### 2.5 冒烟测试

`SmokeTest`（`@Tag("stage00")`，判定面）在骨架上必须**绿**：起一个 order 上下文 + 一个 stock 上下文，
断言两个上下文都拿到了端口、`/actuator/health` 返回 UP、`LabClock` 是那个可推进的实现。
它的作用只是环境体检——这也是为什么它**不出 ticket**（`scope.files_to_change` 非空与「骨架红」两条硬约束都卡死它，
理由见 `_CONTRACT.md` §5），只在 `manifest.stages` 里留一个 `stage-00-onboarding` 名字。

### 2.6 防剧透边界

- **阶段分支里没有任何实现**：`stage-01…stage-05` 各自只比上一级多**本阶段的测试文件**；
- **`-sol` 从同阶段 base 切出**，放截至该阶段的实现；学员看不到它，要在题库里刻意去找；
- **`solutions` 只作总参考**，不作为任何 stage 的 base/head；
- **本 Track 特有的两条**：① `FaultController` 位于 `src/test` 作用域，不会被打进任何运行产物；
  ② 演示档 compose 文件（nacos / zipkin）虽然可见，但里面**没有任何治理配置**（只有服务定义），不构成对 Stage 1–5 的泄题。

| 4 | `stage-04-trace-and-log-correlation` | `[micro-stage-01]` | 红 | 绿 | `src/test/java/com/devteam/micro/stage04/TraceIdPropagationAcceptanceTest.java`、`…/stage04/LogCorrelationAcceptanceTest.java` |

**为什么教学顺序是这样。** Stage 1 是唯一的根：没有「实例清单 + 客户端负载均衡」这个抽象，
后面的超时、熔断、限流、traceId 都无处安放——它们全都长在「订单去调库存」这条客户端调用链上。

**这是一个「一根主干 + 四根平行枝条」的 DAG**（不是一条纯线性链）：

```
        micro-stage-01  (实例清单 + 负载均衡)  ← DAG 根
         /     |      |      \
   stage-02  stage-03  stage-04  stage-05   ← 四条平行枝，彼此不依赖
   (熔断超时) (限流)    (追踪)     (分布式ID·选修)
```

`progression.prerequisites` 里四条枝条都只声明 `micro-stage-01`，**互相之间不声明依赖**：学员完全可能先做限流、
再做熔断。之所以不做成线性，是因为这四件事在真实项目里本来就是独立演进的能力；硬串起来会让
「我改了熔断为什么限流测试变红」这类跨阶段耦合出现，而分支链契约要求「每级只多本阶段测试」，平行枝能天然满足它。

**但分支链本身仍然是线性的**（`_CONTRACT.md` §5）：分支名与 `manifest.stages` 的顺序决定 checkpoint，
所以落地时按 `stage-01 → 02 → 03 → 04 → 05` 逐级叠，每一级只新增本阶段的测试文件。
**DAG 的依赖关系只体现在 `prerequisites` 上，不体现在分支父子关系上**——两者不必一致，也不能强制一致。

**分支链落地命令序列**：

### Ticket 2 · `micro-stage-02`

```yaml
identity:

  schema_version: 1

brief:

    ## 问题背景

    【线上问题｜来自：SRE · 优先级 P0】上周库存服务的数据库做了一次计划外的维护，慢查询变多，
    单个扣减请求从十几毫秒涨到六百毫秒左右。库存服务只是变慢，没有挂；**挂掉的是订单服务**——
    它在三分钟之内把 Tomcat 的 200 个线程全部用光，之后连不碰库存的接口（比如按订单号查询）
    也开始超时。SRE 把订单服务的线程栈打出来，几乎每个线程都停在同一行：等库存服务的 HTTP 响应。

    这一轮事故最贵的地方不是库存变慢，而是**故障顺着调用链爬到了上游**。库存恢复了以后，
    订单服务又自己好了——所以它现在是一个「下游一抖、上游必崩」的结构，扩容订单服务也救不了它。

    ## 问题表现

    订单服务调用库存服务的那个客户端，在建立连接和读取响应这两个阶段上都没有设上限：
    它会一直等下去，等到对方给一个结果为止。下游只是慢的时候，这个「等」会把它自己这边的线程一个个借出去，
    借到没有为止，于是它连自己能立刻回答的请求也答不了了——这是雪崩的第一阶段，
    成因是**上游没有给自己留退路**，而不是下游做错了什么。

    更糟的是每一次这样的失败都要重新走一遍同样的路。库存服务在那三分钟里对每一个请求都答不上来，
    订单服务对每一个请求都照样发过去：它没有任何机制记住「这条路刚刚连着失败了好几次」，
    所以每一次失败都是全新的第一次。这是雪崩的第二阶段——**失败没有被记住，于是被无限重复**。

    库存服务本身没有缺陷，它在那三分钟里确实答不上来，这是事实；订单服务需要做的是在事实不变的前提下，
    不让自己成为第二个受害者。

    ## 你需要完成的修改

    本题需要修改以下文件：

    - `src/main/java/com/devteam/micro/order/client/StockClientImpl.java`：这个客户端现在对「等多久」和
      「等不到算什么」这两件事都没有立场。请给它明确立场：超过给定上限还没拿到结果，这一次调用就算失败；
      连接建立不起来，也算失败。两类失败都要能被上层的容错组件识别成「失败」而不是别的什么东西。
    - `src/main/java/com/devteam/micro/order/service/OrderService.java`：这里目前把下游异常直接冒泡出去，
      调用方拿到的是 500。请让它在下游不可用时仍然能给出一个**业务上可解释的结果**——
      调用方需要能区分「下单成功」「库存不足」和「暂时办不了」这三种情况，而不是只能靠 HTTP 状态码猜。
    - `src/main/java/com/devteam/micro/order/config/ResilienceConfig.java`：容错组件已经作为依赖引入并被装配，
      但配置里只有名字，没有窗口、没有阈值、没有打开时长，也没有任何地方把下游调用真的交给它。

    有一条约束是判据能成立的前提，请务必守住：**打开状态的判定必须基于「次数」而不是「时间」**
    （也就是说，规则由一个固定长度的调用记录窗口决定，而不是由一段时钟区间决定）。
    原因很直接：基于时间的窗口会让同一份代码在不同负载的机器上给出不同结果，而这道题的判据要在学员机器上离线复现。

    另外，下游被调用的次数是可观测的（库存侧会在响应头里回显它这一路被调用了多少次），
    这个数字是这道题里唯一能区分「降级」和「熔断」的东西：降级让调用方拿到一个体面的结果，
    熔断让下游**不再被调用**。两者都要有。
```

## Stage 1 · 注册发现 & 负载均衡 ⬜

**亲手场景**：库存扩到两台却全部流量打在第一台 → 你补齐客户端选路与故障摘除，让滚动重启不再等于全站故障。

|------|-----------|--------|

## Stage 2 · 熔断降级 & 超时 ⬜

**亲手场景**：下游慢 600ms 就把上游线程等干 → 你补超时与熔断，让失败不再被无限重复。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 雪崩与级联失败 | 上游线程/连接被慢下游占满，故障顺着调用链向上蔓延 | 一个下游变慢为什么会拖垮整个系统？ |
| 超时与快速失败 | 给等待设上限，把「慢」转成「失败」，避免资源被无限占用 | 超时值怎么定？定得太小会怎样？ |
| 熔断器三态 | 关闭态统计失败；达到阈值进打开态直接拒绝；到期进半开态放少量探测 | 熔断器三个状态之间怎么转换？ |
| 计数窗口 vs 时间窗口 | 计数窗按「最近 N 次调用」统计，结果与负载无关；时间窗按区间统计，受机器与流量影响 | 生产上你选哪种窗口？为什么？ |
| 降级与兜底响应 | 熔断之后必须给出可解释的业务结果，否则调用方只能靠状态码猜 | 降级返回什么才对调用方友好？ |
| 隔离（线程池 / 信号量） | 把不同下游的等待资源分开，一个下游的慢不占满全部资源 | 线程池隔离和信号量隔离怎么选？ |
| 熔断恢复与半开探测 | 打开一段时间后放少量请求试探，成功才关闭 | 半开期探测失败会怎样？ |

**亲手场景**：一个人拿脚本把下单接口刷爆 → 你补按调用方的配额与快速拒绝，并让额度恢复可被观测。

|------|-----------|--------|
| 链路追踪与 traceId | 一次外部请求分配一个标识，跨服务跨线程一路携带 | traceId 是怎么保证全局唯一的？ |
| MDC 与日志上下文 | 日志框架从与线程绑定的上下文里取字段，每行自动带上 | 为什么日志里能自动打印 traceId？ |
| 跨进程上下文传播 | 出站请求要把当前上下文写进请求头，入站再从请求头恢复 | traceId 怎么跨服务传递？ |
| 跨线程与异步传播 | 线程池换线程时上下文不会自动跟随，需要显式传递或装饰 | 异步/线程池里 traceId 为什么会丢？ |
| 采样 | 只上报一部分链路以控成本，采样率与「恰好没采到」是一对矛盾 | 采样怎么做才不丢关键请求？ |
| traceId 与 spanId | traceId 串起一次调用，spanId 标识其中一段，父子关系构成调用树 | traceId 和 spanId 有什么区别？ |
| 链路可视化与耗时分析 | 采集端聚合各段耗时，才能回答「哪一段最慢」 | 怎么定位一次请求里最慢的一段？ |

## Stage 5 · 分布式 ID & 幂等 ⬜

**亲手场景**：同一毫秒生成的两个订单号撞在一起 → 你给编号加上实例段与序号，并让冲突有第二条路。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 分布式 ID 的要求 | 全局唯一 + 趋势递增 + 高可用 + 信息安全（不泄露业务量） | 分布式 ID 有哪些方案？各有什么取舍？ |
| 雪花算法 | 时间戳 + 实例段 + 序列号拼成 64 位，靠「同毫秒内序号自增」保证唯一 | 雪花算法的位宽怎么分配？ |
| 号段模式 | 一次取一批 ID 缓存在本地，用完再取；避免每次访问中心 | 号段模式和雪花怎么选？ |
| 时钟回拨 | 时间倒流会让后生成的 ID 小于先前的，破坏趋势递增 | 时钟回拨怎么处理？ |
| 实例编号分配 | 实例段必须唯一且重启后稳定，通常由注册中心或配置下发 | workerId 怎么保证不重复？ |
| 唯一索引兜底 | 数据库唯一约束是最后一道防线，命中它意味着要换一条路 | 唯一键冲突之后应该怎么办？ |
| 幂等与重试的区别 | 重复提交要「不产生第二次副作用」，ID 冲突要「换一个号重来」，两者判定依据不同 | 怎么区分重复提交和 ID 冲突？ |

### 6.1 判定面逐条论证

### 6.2 必须 pin 的东西

- **文件摘要**（由骨架仓的 `scripts/digest-pin.sh` 生成，配方照抄 `seckill-lab` 的同名脚本）：
  `compose` / `build` / `tests` / `sim` 四个键分别覆盖 `runtime` 里对应的四个入口。
  **`tests` 的摘要对象是「`src/test/java/com/devteam/micro/stage*/` 下的全部文件」，且必须把
  `stock-service/src/test/` 下的故障注入端点也算进去**——否则有人改了注入器就能改变判据的下游行为。
- **镜像摘要**（多镜像，逐个 pin）：`mysql:8.0`、`redis:7` 是常用档；`nacos/nacos-server:v2.x`、`openzipkin/zipkin` 是演示档
  （虽然不在 `runtime.compose` 里，但它们出现在判定面 `./docker/` 之下，属于「学员机器上会跑的东西」，一并 pin）。
  取值命令与架构注意事项照抄 `seckill-lab` 的注释：`docker image inspect --format '{{.RepoDigests}}' <image>`，
  **digest 与架构绑定**（arm64 机器拉到的多架构 manifest 会给出不同 digest），按本机输出更新即可。
- **Maven 依赖的漂移**（本 Track 特有的诚实说明）：`mysql`/`redis` 这类镜像摘要锁不住 `spring-boot-starter-*`、
  `resilience4j-*`、`spring-cloud-loadbalancer` 这些 jar。缓解办法有两条且都不是密码学保证：
  ① 依赖**不带版本区间、不用 `LATEST`/`RELEASE`**，版本写在父 POM 的 `<properties>` 里；
  ② 可选的更强做法是 pin `mvn dependency:tree` 的输出摘要（写进 `digest_pin.deps`，作为本 Track 的自定义键），
  它不阻止恶意仓库投毒，但能让「依赖树悄悄变了」变成一次可见的 diff。默认环境可离线构建（`~/.m2` 预热）。

### 6.3 供应链注意

本 Track 在学员机器上会执行的东西有：`scripts/build.sh`（Maven 构建）、四个 `pom.xml` 声明的依赖树、
canonical 测试（Java 代码，会被编译执行）、`docker compose` 起的三个镜像。其中**第三方二进制**只有那三个镜像；
**没有引入任何 agent（探针/字节码增强）**——这是刻意选择（见 §1.0.1 的 Sentinel 那一行），
因为 agent 会在 JVM 启动参数层留下无法被 schema 表达的额外执行入口。

**离线依赖**：交付前必须在目标环境跑一次 `mvn -o -DskipTests test-compile`，把 `~/.m2` 预热；
这是「判据能在学员本机离线复现」的必要条件（`_CONTRACT.md` §8 第一条），必须写进 Track 的入职任务书。

### 6.4 `manifest.requires`（内存门槛要写进去）

```yaml
  manifest:
    requires:
      java: "17"
      build: maven
      docker: "24"          # 仅常用档/演示档需要；默认档不需要
      memory_gb: "4"        # 见下：判据档实测 1.1–1.4GB，常用档 1.5–1.9GB，留一倍余量
```

为什么把内存写进 `requires`：平台据此**体检**（`_CONTRACT.md` §2 注释「仅声明，平台据此体检，不代装」），
而本 Track 的资源门槛是这份规格里两个先决取舍之一（§1.0.1）。写 `4` 的理由：判据档实测 1.1–1.4GB，
常用档 1.5–1.9GB，但学员机器上还有 IDE 与其它进程——把余量留足，宁可让 3GB 的机器在体检阶段被劝退，
也不要让它跑到一半开始换页然后给出一个假红。

### 6.5 `trust_level` 建议

`self`：骨架与判据由 Track 作者自己维护，尚无第三方贡献者。
升 `verified` 需要三件事：① `contribute.review.signed_by` 有维护者签名；② 上述多镜像与脚本摘要全部锁定
（即 `digest_pin` 里没有 `<待生成>` 占位）；③ 一条 CI 记录证明「骨架红 / 五个 stage 的 `-sol` 绿」。

## 7. 风险、妥协与工作量

| 风险 | 影响 | 缓解 |
|---|---|---|
| **熔断器默认按时间窗统计**，测试期间机器负载不同会给出不同结论 | Stage 2 判别性门（假红/假绿） | 测试**显式**把窗口类型配成计数窗（`slidingWindowType=COUNT_BASED` + 显式窗口长度），并把这条写进 `graded` 的断言注释；题面把「基于次数」写成硬约束 |
| **限流器内部自己取系统时间** | Stage 3 判据要么依赖 sleep（慢 + 抖动），要么不可判定 | 骨架提供 `LabClock`，题面与 `concepts` 都指向「时间必须可注入」；测试用 `advance()` 而非 `sleep()`；`RefillTokenBucket` 的构造签名里就有 `LabClock`（缺陷在于没用它，而不是不在） |
| **进程内多上下文互相干扰**（Bean 覆盖、端口争用、`spring.application.name` 相同导致上下文缓存键冲突） | 全部 stage 的假红 | `LabRuntime` 统一管理：两个上下文都用独立 `SpringApplicationBuilder` 实例、各自设置服务名与 `server.port=0`、测试内**禁用缓存**（`@DirtiesContext(AFTER_CLASS)`）；§1.1 的备选方案 B 是安全网 |
| **`@DynamicPropertySource` 与「先起上下文再注入端口」的循环依赖** | Stage 1 无法落地 | 首选显式手动起上下文 + 可变属性源；备选方案 B（把实例列表改为可注入的 provider）；两者对题面与判据**完全等价**，切换不需要改题 |
| **日志收集器在并行测试下互相污染** | Stage 4 假红 | `pom.xml` 里关掉 surefire 并行；收集器按 traceId 分桶并在 `@BeforeEach` 清空 |
| **`X-Lab-Instance` / `X-Lab-Calls` 这类观测头被学员「顺手实现」而没真做治理** | Stage 1/2 的假绿 | 两个头由**库存侧骨架**（判定面之外的 `StockController`，★已绑好）无条件回显，学员的改动面碰不到它；`StockClientImpl` 的改动面里也不含它 |
| **演示档 compose（Nacos / Zipkin）被误当成判据依赖** | 判据在低配机器上假红 | 两份文件都不在 `runtime.compose`；`SmokeTest` 与五个 stage 的测试都不引用它们；§1.0.1 的「砍的顺序」写明它们先被砍 |
| **依赖树漂移**（Maven 侧无法用镜像摘要锁死） | 供应链（`_CONTRACT.md` §13 的威胁模型） | 版本写死在父 POM、不用版本区间；可选 pin `mvn dependency:tree` 摘要（§6.2）；`~/.m2` 预热后离线构建 |
| **题面泄漏解法** | 准入门 D2 门（`brief` / `concepts` / `hints` 扫解法行） | 五张卡各带一份泄漏自查（§4 每张末尾）；`concepts` 只用面试考点名，不用 API 名；hints 一律以问句收束 |
| **与 `mq-lab` 的重叠随迭代漂回** | 内容重复，两条 Track 争同一个考点 | §1.0.2 的三条落地方式（manifest 不列、外链不复制、Stage 5 题面写范围禁令）；地图末尾用「已由 mq-lab 覆盖」一节承接 |
| **Stage 5 的「同一毫秒 200 次生成」在极慢机器上溢出序号段** | 单条用例偶发红 | 序号耗尽时转向下一毫秒（不判红），断言只看唯一性与顺序；这一条写进断言的注释与 `expect` |
| **端口的宿主机占用**（18080/18081/18082 与 13306/16379/18848/19411） | 手玩档起不来 | 默认的 canonical 测试全部用 `server.port=0`，**判据与端口无关**；手册里的固定端口只用于手玩，已避开常用默认端口 |

**建议的实施顺序**（先做判据最硬、最能验证契约的那一张）：

1. **先做 Stage 2**。它是本 Track 唯一的「硬判据」样板：计数窗 + 固定延迟 + 降级形状三件事一次把
   「微服务治理考点能不能进 canonical 测试」这个总问题回答掉。它同时逼出 `LabRuntime`（两个上下文 + 故障注入端点），
   而这正是后面四张卡共用的基础设施——**先搭骨架里最难的那块，别先用 Stage 1 试水**。
2. **再做 Stage 1**。它是 DAG 根、`prerequisites` 的锚点，但技术上比 Stage 2 简单（只用两个健康实例 + 一个死端口），
   在 Stage 2 铺好的 `LabRuntime` 上一天可完成。
3. **然后 Stage 3**（注入时钟那条链路此时已就绪）与 **Stage 4**（日志收集器此时已就绪），两张可并行。
4. **最后 Stage 5（选修）**，并在同一轮里把 `README.md` 的 stage 数从 `4~6` 改成 `5`、把 `track.yaml` 的 `manifest.stages` 补齐。
5. **准入门前先跑一遍 `_CONTRACT.md` §4 的判别性**：每个 stage 分支红、每个 `-sol` 绿、且红在业务缺陷（不是 `Connection refused`）。
